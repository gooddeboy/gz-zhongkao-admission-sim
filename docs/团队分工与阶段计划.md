## 3. Git 协作约定

- 主分支 `main` 保持可运行；功能分支命名 `feature/<模块>`，修复分支 `fix/<问题>`。
- 提交信息使用动词开头，例如：
  - `feat: implement gradient admission engine`
  - `test: add small dataset manual expectations`
  - `docs: add deployment guide`
- 合并前至少一名其他成员 review；合并后运行 `pytest`。
- 每个阶段打一个 tag（如 `v0.1-requirements`、`v0.5-engine`、`v1.0-delivery`）。
- 不提交 `data/admission.db`、快照、`__pycache__`、个人密钥。

## 4. 贡献记录建议

为避免“挂名”，建议每人保留可核验证据：

- 代码提交记录（Git author + commit hash）；
- 测试用例或缺陷单；
- 文档章节作者；
- 演示时负责讲解的模块；
- 会议记录/任务看板截图。

## 5. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 规则理解偏差 | 投档结果错误 | 先做小数据集人工推演，再写完整引擎；每批与任务书逐条对照 |
| 梯度/志愿顺序实现错误 | 核心验收失败 | 单独测试“梯度优先”“同梯度志愿优先”“同分序号” |
| 名额结转重复计算 | 计划超额 | 每次运行从初始状态重建；结转流水 + 平衡等式校验 |
| 数据规模导致性能问题 | 演示卡顿 | 大数据使用摘要追踪；分页查询；必要索引 |
| 前后端联调延迟 | 演示不完整 | 先定义 API 契约，再并行开发；用 TestClient 做接口测试 |
| 成员投入不均 | 协作分低 | 每周任务看板 + Git 记录 + 互评 |
| 提交前环境不一致 | 无法复现 | 固定 Python 版本、requirements、部署说明；提交前从空库跑一遍 |

- [ ] 设计报告、测试材料、演示脚本齐全；
- [ ] Git 历史与分工记录真实可核验。
