# 团队分工与阶段计划

> **说明**：最新版任务书允许每组 **1–8 人**，本组为 **3 人**。下表姓名、学号请替换为真实信息；贡献占比为建议值，必须根据实际投入调整，合计 100%。不得伪造协作记录。
>
> 分组名单以任课教师腾讯文档为准：<https://docs.qq.com/sheet/DTHR2UkFPa1RRbGNY?tab=000001>。

## 1. 成员与角色

| 成员 | 学号 | 角色 | 负责模块 | 建议占比 |
| --- | --- | --- | --- | --- |
| 组长（姓名待填） | 待填 | 项目经理 / 核心算法 / 系统集成 | 需求与规则、投档引擎、运行编排、快照与版本、Git 与最终集成 | **40%** |
| 成员B（姓名待填） | 待填 | 数据建模 / 数据管理 / 测试 | ER 图与表结构、CRUD 与导入、数据校验、数据生成、pytest 测试 | **30%** |
| 成员C（姓名待填） | 待填 | 前端 / 统计与结果 / 文档部署 | Web 界面、结果查询、统计导出、滑档案例页面、部署与演示材料 | **30%** |

## 2. 详细职责

### 2.1 组长（40%）：项目经理 / 核心算法 / 系统集成

**负责模块**

- 需求与范围：拆解任务书，编写规则清单，确定简化范围与验收口径；
- 核心算法：梯度计算、四批投档、名额分配隔离、计划结转、同分排序、一致性校验；
- 运行编排：创建运行、输入快照、数据版本锁定、按批/完整执行、计划余额与结转流水；
- 系统集成：API 骨架、运行接口、前后端联调、最终合并与演示；
- 项目管理：任务分解、进度跟踪、Git 分支与代码 review、风险处理。

**对应文件**

- `app/engine.py`：四批次投档引擎、梯度、结转、`verify_run`；
- `app/db.py`：运行创建、快照、锁定、批次执行、状态持久化；
- `app/main.py`：API 骨架、运行与校验接口；
- `docs/需求与规则清单.md`、`docs/核心算法.md`。

**交付物**

- 可运行的四批次投档引擎；
- 运行快照与数据版本机制；
- 系统集成版本与最终演示；
- Git 主分支合并记录。

**答辩讲解**

- 四批次顺序、梯度优先、同梯度志愿优先；
- 名额分配隔离与结转；
- 为什么不能按总分逐人扫描全部志愿；
- 一致性校验与系统约束。

### 2.2 成员B（30%）：数据建模 / 数据管理 / 测试

**负责模块**

- 数据建模：ER 图、表结构、字段说明、约束、索引；
- 数据管理：高中、初中、考生、招生计划、自主招生资格、志愿的 CRUD；
- 数据导入：CSV 导入、行级校验、全有或全无回滚；
- 数据生成：small / medium / demo / full 预设，固定随机种子；
- 测试：小数据集设计、人工预期、pytest 自动化测试、边界与异常测试、测试材料。

**对应文件**

- `data/schema.sql`：数据库结构、约束、索引；
- `app/validation.py`：输入数据校验；
- `app/repository.py`：输入数据 CRUD；
- `app/importer.py`：CSV 导入；
- `app/generator.py`：可重复生成的虚构数据；
- `tests/`：pytest 测试；
- `docs/数据库设计.md`、`docs/测试材料.md`。

**交付物**

- ER 图、表结构与字段说明；
- 数据管理、导入与校验功能；
- 小数据集与人工预期；
- 45 项自动化测试与测试材料。

**答辩讲解**

- 为什么名额分配要保留初中；
- 同分序号与唯一约束；
- 异常输入如何拒绝；
- 测试场景如何覆盖梯度、志愿、边界和结转。

### 2.3 成员C（30%）：前端 / 统计与结果 / 文档部署

**负责模块**

- 前端：概览、数据管理、投档执行、结果查询、统计分析、滑档案例、帮助页面；
- 交互：表格分页、搜索筛选、弹窗表单、CSV 导入、运行进度、图表；
- 结果与统计：按考生/高中/计划/批次查询，未录取原因展示，最低分与末位考生，CSV 导出；
- 滑档案例页面：基线与志愿调整后的对照展示；
- 文档与部署：README、部署说明、演示脚本、截图、报告排版。

**对应文件**

- `app/static/index.html`、`app/static/styles.css`、`app/static/app.js`；
- `app/stats.py`：结果查询、统计、导出；
- `app/cases.py`：滑档案例；
- `app/main.py`：统计、结果、案例相关接口；
- `docs/部署说明.md`、`docs/演示脚本.md`、`docs/设计报告.docx`（排版与截图）。

**交付物**

- 可演示的 Web 系统；
- 结果查询与统计导出；
- 两个滑档案例的对照页面；
- 部署说明与演示材料。

**答辩讲解**

- 页面操作流程；
- 最低录取分与末位考生的区别；
- 滑档案例的志愿调整与挤出效应；
- 如何启动、初始化和复现。

## 4. Git 协作约定

- **每人使用自己的 GitHub 账号提交**，不要共用同一个账号；提交作者应与分工表一致。
- 分支建议：
  - 组长：`feature/engine`、`feature/run`、`integration`；
  - 成员B：`feature/data`、`feature/import`、`test/`；
  - 成员C：`feature/ui`、`feature/stats`、`docs/`。
- 提交信息使用动词开头，例如：
  - `feat: implement four-batch admission engine`
  - `feat: add candidate import and validation`
  - `feat: add statistics page and CSV export`
  - `test: add boundary and quota isolation cases`
  - `docs: add deployment and demo guide`
- 合并前由组长或至少一名其他成员 review；合并后运行 `pytest`。
- 每个阶段打 tag，例如 `v0.2-model`、`v0.5-engine`、`v1.0-delivery`。
- 不提交 `data/admission.db`、快照、`__pycache__`、个人密钥。

> 如果当前仓库的历史提交主要来自组长账号，应如实说明：代码由组长主写，B/C 负责测试、数据、前端或文档；或者让 B/C 在后续实际修改中用自己的账号提交。**不要为了凑分工伪造 commit。**

## 5. 贡献占比与依据

建议占比：**组长 40% / 成员B 30% / 成员C 30%**。

可核验依据：

- Git 提交记录（作者、commit hash、修改文件）；
- 测试用例与测试材料；
- 文档章节作者；
- 演示时负责讲解的模块；
- 会议记录或任务看板。

如果实际投入与建议占比不同，按真实情况调整，但三人合计必须为 100%。

## 6. 个人工作说明模板

每位成员提交一段个人工作说明，建议包含：

1. 负责的模块与文件；
2. 关键实现或设计思路；
3. 遇到的困难与解决办法；
4. 参与的测试与验证；
5. 答辩时负责讲解的内容。

示例：

> 本人负责投档引擎与运行编排，主要实现 `app/engine.py` 的四批次投档、名额分配隔离、计划结转和 `verify_run`，并在 `app/db.py` 中实现运行快照、数据锁定和按批执行。测试方面参与了小数据集人工推演和结转平衡校验。答辩时负责讲解梯度优先、志愿轮次和结转规则。

## 7. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 三人对规则理解不一致 | 投档结果错误 | 先共同确认规则清单，再用小数据集人工推演 |
| 核心算法集中在组长 | 进度风险 | B/C 尽早介入测试和页面联调，组长提前拆接口 |
| 前端与后端接口不一致 | 联调返工 | 先定 API 契约，使用 `/docs` 和 TestClient 验证 |
| Git 冲突 | 代码丢失 | 小步提交、按模块分支、合并前 review |
| 测试造假或预期倒填 | 验收失败 | 人工预期先写，测试输出只用于对照 |
| 贡献占比不实 | 协作分低 | 用 Git 记录、测试、文档和演示讲解佐证 |
